# 大型3D游戏画面技术与本项目可行性调研

调研日期：2026-11-02。项目基准：**0.3.3 / build 6，提交743c269，Godot 4.6.3**。本报告包含开发者公开资料、源码核对和本机隔离实验；没有将实验画质写入游戏、安装包或正式服。

后续已在本地实施[地表/环境材质](../assets/terrain/SURFACE_NOTES.md)和[环境美化/单人建造](建造模式.md)，尚未发布。本报告的“当前”与实验数字均指上述0.3.3提交，不代表后续工作区状态；最新验证见[验证基线](验证基线.md)。

我的建议是优先改善**光照和色彩层次、材质区别、近景细节、局部氛围与画面稳定性**。本项目的柔和卡通风格适合借鉴大型游戏组织画面的方式。全岛动态GI、光追、超密植被和可穿行体积云需要更高成本，暂不进入默认画质方案。

**大型游戏如何形成“惊艳感”**

下面按公开资料的具体版本说明技术，避免把首发方案当作所有后续补丁的现状。2025—2026年的资料用于了解近期进展，较早的SIGGRAPH资料用于解释仍有参考价值的方法。

| 公开案例 | 形成视觉效果的方法 | 对本项目的启发 |
| --- | --- | --- |
| 《刺客信条：影》：2025技术问答、2026 Anvil介绍 | 天气、风、季节、植被和光照相互响应；微多边形改善细节连续性；不同模式采用不同光照取舍 | 让树叶、天空、窗光、地面颜色共同表达天气和时间；先保证可扩展的光照层次 |
| 《心灵杀手2》：2023 Northlight、2024 PS5 Pro方案 | 精细可见性裁剪、材质、色彩制作、雾和反射形成统一氛围；在有限分辨率内重建高质量画面 | 近景与远景分配不同预算，先组织灯光、冷暖和空间深度，再增加重特效 |
| 《堡垒之夜》：2022 UE5.1公开方案 | 卡通风格也使用精细阴影、反弹光、材质反射和时序重建 | 卡通画面可以有可信的光照和材质，保留简洁造型也能提升质感 |
| 《地平线》：2022 Nubis及2023《炙炎海岸》 | 有设计的云层体积、透光、远近层次，随游戏体验扩大技术投入 | 我们目前主要在地面活动，可先改善天空色彩、云影和远景空气透视 |
| 《对马岛》：2021开发者演讲 | 物理光照基础配合主动艺术调整，利用雾、风、光向和色调建立电影式构图 | 明确主体、背景、光向和冷暖；避免场景各处同样亮、同样饱和 |
| 《DOOM: The Dark Ages》：2025路径追踪更新与引擎负责人访谈 | 路径追踪、降噪、超分辨率、几何加速结构和专门优化协同工作 | 把光追视作完整的渲染研发项目，不能把它等同于一个低成本开关 |

这些案例同时展示了预算限制。Ubisoft在2025首发技术问答中解释，为保留其他渲染改进，60帧模式采用混合GI方案；不能据2026介绍中对RTGI的概述，推断所有平台/模式都使用相同光照路径。[Ubisoft问答](https://www.ubisoft.com/en-gb/game/assassins-creed/news/4XbPPtFyQEtIMWrA9xVDmZ)

Remedy在2024 PS5 Pro说明中，将光追反射放在30帧画质模式；60帧模式采用1536×864内部渲染，再输出4K。Epic当前Lumen性能指南给出的主机目标预算为1080p下约4ms／60帧档和8ms／30帧档，并配合TSR。这些是各自引擎和硬件上的预算，不能直接当作Godot或M1 Pro的耗时。[Remedy模式说明](https://www.remedygames.com/article/alan-wake-2-on-playstation-5-pro---behind-the-scenes)、[Epic Lumen性能指南](https://dev.epicgames.com/documentation/en-us/unreal-engine/lumen-performance-guide-for-unreal-engine)

**本项目已经具备什么，差距在哪里**

源码核对范围为城市/山谷生成器、运行时光照、房屋材质、工具材质、画质预算与项目设置。定位见[城市光照](../scripts/city/city_world.gd)、[城市生成](../scripts/city/build_city.gd)、[渲染预算](../scripts/city/render_budget.gd)、[房屋材质](../assets/shaders/home_surface.gdshader)、[海面](../assets/shaders/island_ocean.gdshader)、[工具](../scripts/city/tool_models.gd)。

| 当前实现 | 实际含义与改善机会 |
| --- | --- |
| Forward+；Mac Metal，Windows D3D12；4×MSAA | 已有现代实时光照基础，轮廓清楚；需要保持三物种描边、细格纹和移动时的稳定性 |
| 均衡模式将3D限制在约200万像素，UI维持输出分辨率 | 已经采用大作常用的分辨率预算思路；Mac用MetalFX Spatial，其他Forward+用FSR空间缩放，并非DLSS/时序重建 |
| 实时太阳/阴影、SSAO、少量局部阴影灯、随昼夜变化的环境色 | 基础完整；全局环境光仍较均匀，室内明暗主要靠手工灯和环境色混合，缺少空间相关反弹光 |
| 城市生成器关闭环境反射，运行时Forward+保持Linear色调映射 | 可探索更好的高光保留和反射，但需要联动曝光、配色及室内外过渡 |
| 建筑常用程序纹样，粗糙度偏高；木、铜工具通过颜色/粗糙度区分 | 铜工具当前没有设置金属度；可以先增加少量清晰的材质区别，避免所有物件都像同一种哑光材料 |
| 海面为unshaded程序动画，山谷水体已有分段流动与泡沫 | 直接开启SSR不代表海面就会获得真实反射；水体需要专门的材质方案 |
| 已有分区合批、远景简化、花丛、少量动态环境效果 | 可以继续优化可见性与细节层次；本轮菜园视角仍记录约1,523次绘制提交，单看低多边形不能判断瓶颈 |

这些是实现事实及对源码的分析，不能据此断言某个参数就是所有“泛白”或卡顿的唯一原因。

**本机实际成本：逐项开启，不改变游戏文件**

在Apple M1 Pro／14核GPU／16GB内存上，以Godot 4.6.3、Metal Forward+运行。输出1920×1080，3D缩放约0.982，实际约200万像素，4×MSAA；关闭帧率上限及VSync。三个固定视角为菜园日景、工坊夜间外立面、山谷桥日景。冻结地图场景节点（角色/NPC等）、隐藏HUD；Session计时与着色器TIME继续运行。

每种设置预热60帧，采样约1.4秒；按正序和逆序各一轮，共**48组、7,359帧**。表中为两轮中位数的均值，测量的是`frame_post_draw`之间的墙钟间隔，包含渲染提交/同步等因素，**不是GPU纯时间，也不是完整玩法帧率承诺**。固定日志、脚本、原始值和限制见[实验记录](evidence/graphics-research-20261102/summary.json)。

| 单项设置 | 菜园日景 | 工坊夜景外立面 | 山谷桥日景 | 相对当前基线的判断 |
| --- | ---: | ---: | ---: | --- |
| 当前基线 | 9.73ms | 9.29ms | 7.94ms | 作为比较起点 |
| 仅切换AgX | 9.83ms | 9.03ms | 7.77ms | 差异-0.26～+0.09ms，接近短测噪声，不能说它能提升性能 |
| 开启天空反射 | 10.00ms | 9.48ms | 8.15ms | +0.19～0.27ms |
| 开启SSIL，强度0.6 | 11.28ms | 10.55ms | 9.28ms | +1.25～1.54ms |
| 开启Glow，强度0.4 | 10.07ms | 9.71ms | 8.30ms | +0.34～0.42ms |
| 开启体积雾，密度0.015、默认质量 | 9.97ms | 9.55ms | 8.04ms | +0.10～0.26ms，仅代表当前少量灯和默认雾网格 |
| 开启SSR，默认质量 | 10.63ms | 10.02ms | 8.89ms | +0.73～0.95ms |
| 关闭现有SSAO | 8.76ms | 8.49ms | 6.83ms | 节省0.80～1.11ms，失去部分接触层次 |

单独开启SSIL约相当于60帧总预算的7.5%～9.3%，并非游戏帧率一定下降这个比例。60／90／120帧分别只有16.67／11.11／8.33ms；完整游戏还需要承担角色、导航、交互和网络负载。CPU和GPU会并行，不能把所有监视值直接相加。

此次使用默认质量的体积雾成本较小，不表示大范围高精度体积光、许多阴影灯或体积云也便宜。雾质量、计算距离和灯光交互都会改变成本；局部FogVolume仍需要体积雾框架，不能按占屏面积简单折算。[Godot体积雾说明](https://docs.godotengine.org/en/4.6/tutorials/3d/volumetric_fog.html)

实验另有一次SDFGI尝试，预热阶段未产出有效测量，已中止并排除，不能据此给出耗时或判定引擎缺陷。VoxelGI、LightmapGI、探针捕获、密集植被、动态建造和光追没有在本轮测量。`TIME_PROCESS`监视值受到前序截图等工作影响，显存计数包含缓存，二者均未用于推导单项CPU/显存成本。

**视觉复核得到的取舍**

AgX默认参数下，现有明亮配色明显变灰，白墙高光保留更多，但主体的鲜明感也下降。正式采用时需要重做曝光、对比、饱和度及白色角色校准；应将Linear、ACES、AgX放在相同美术目标下比较。Godot也明确说明不同色调映射有不同处理方式，AgX并非零成本。[Godot色调映射](https://docs.godotengine.org/en/4.6/tutorials/3d/environment_and_post_processing.html#tonemap)

全局体积雾密度0.015使山谷前景也蒙上一层灰，虽然帧时间增加较小，效果不适合直接用作晴天默认值。更合适的方向是保留清晰近景，在溪谷、瀑布或清晨使用有边界的薄雾，保持操作目标清楚。

天空反射需要能显示其效果的材质；大多数现有物件较粗糙，单独开启的收益有限。铜工具、玻璃和水等重点物件先有明确材质定义，再配置反射来源，会比全场统一降低粗糙度更可控。

基线、AgX和体积雾的4张代表性预览保存在[实验目录](evidence/graphics-research-20261102/README.md)，用于说明取舍。其余可再生QA副本已清理，这些图不是最终画质提案。

**各类技术在Godot项目中的可用路径**

| 方案 | 对画面的具体作用 | 可行性及主要消耗 | 建议 |
| --- | --- | --- | --- |
| 色调映射、曝光、色彩脚本、冷暖与明暗分组 | 白墙保留层次，角色从背景中分离，昼夜更有情绪 | 现有Environment可用；更换色调映射本机差异较小；主要投入是美术调校 | 第一优先 |
| 材质粗糙度/金属度、适度法线、少量真实倒角 | 铜、木、布、石、水有不同的受光特征 | 基础PBR已具备；贴图增加采样、内存与包体，倒角增加顶点；仅在可见尺度上增加 | 第一优先 |
| 天空反射、局部ReflectionProbe | 铜器和玻璃能反映天空/房间，减少“塑料色块感” | 天空反射已测；局部探针捕获未测。Once模式捕获后较便宜，Always模式持续重绘周围场景 | 优先小范围验证 |
| 现有SSAO和接触阴影微调 | 脚底、井沿、家具与墙角更有接触感 | SSAO已在使用；本机关闭可省约0.8～1.1ms；范围太大易使卡通模型显脏 | 保留并优化，不盲目叠加 |
| SSIL | 屏幕内小尺度反弹光、动态物件附近颜色呼应 | Forward+可用；已测约+1.25～1.54ms；有离屏信息缺失与时序问题 | 高画质可选，先验证室内价值 |
| LightmapGI＋动态物件光照探针 | 静态房屋有细腻反弹光，运行时开销较低 | 需要UV2、烘焙、额外资源和制作流程；动态物件从探针接光。布局变化会使烘焙假设失效 | 用固定小房间原型验证 |
| 局部VoxelGI | 房间有动态光源和反弹光 | 需要体素烘焙，GPU成本较高；改变静态几何需重烘焙，Dynamic模式更贵 | 先做单房间高画质原型 |
| SDFGI | 大范围、随相机更新的间接光 | Forward+支持，但并不支持连续动态遮挡物；级联更新、漏光和移动稳定性需单独验收，本轮无有效耗时 | 放在后续研究 |
| 薄雾、局部光束、轻微Glow | 建立前中后景和灯光氛围 | 体积网格、透明重叠、额外缓冲；时序重投影可产生拖影 | 仅用于合适地点/时段 |
| 稀疏植被、统一风场、局部粒子 | 世界有持续的小变化 | 顶点动画与分区MultiMesh可复用；大面积透明叶片和带阴影植被会增加过绘与阴影成本 | 场景设计控制密度 |
| SSR或平面反射 | 平滑水面/地面反映附近物体 | SSR已有测量但依赖屏幕信息；平面反射通常要额外渲染视角，未测成本；现有海面需改材质 | 对重点水域专项验证 |
| LOD、遮挡裁剪、分区批处理 | 用节省的预算支持更好的近景 | 会增加制作和CPU管理工作；不能保证所有视角都受益 | 与画质方案一起做 |
| 硬件光追/路径追踪、Nanite式几何 | 更完整的光线交互与高几何密度 | 不是本项目Godot 4.6.3现有配置的直接开关；需要引擎/扩展、硬件、资产管线和跨平台研发 | 当前不作为主路线 |

上述Godot能力分别参照[反射探针](https://docs.godotengine.org/en/4.6/tutorials/3d/global_illumination/reflection_probes.html)、[SSIL](https://docs.godotengine.org/en/4.6/tutorials/3d/environment_and_post_processing.html#screen-space-indirect-lighting-ssil)、[LightmapGI](https://docs.godotengine.org/en/4.6/tutorials/3d/global_illumination/using_lightmap_gi.html)、[VoxelGI](https://docs.godotengine.org/en/4.6/tutorials/3d/global_illumination/using_voxel_gi.html)、[SDFGI](https://docs.godotengine.org/en/4.6/tutorials/3d/global_illumination/using_sdfgi.html)、[材质](https://docs.godotengine.org/en/4.6/tutorials/3d/standard_material_3d.html)。渲染器兼容性以[Godot 4.6功能表](https://docs.godotengine.org/en/4.6/tutorials/rendering/renderers.html)核对，不能假定Forward+效果都能出现在Compatibility路径。

反射探针主要解决镜面环境信息，不等于完整反弹光。SSAO只解决部分接触遮蔽；SSIL依赖屏幕信息，适合作为补充，也不等于完整GI。[Godot GI对照](https://docs.godotengine.org/en/4.6/tutorials/3d/global_illumination/introduction_to_global_illumination.html)

**与未来建造模式有关的关键限制**

1. 建造物件的视觉、碰撞、挂点之外，还应保留光照/遮挡代理与更新范围。移动、旋转、删除后按区域更新，避免每件家具变动都重算全岛。
2. LightmapGI适合固定布局。可以研究同一封闭模块整体搬动时复用局部烘焙，但外部日照和遮挡改变仍需处理；拆墙、改门窗或重排家具会破坏原先的光照关系。角色能从烘焙探针接光，不代表移动家具会自动重算反弹光。[LightmapGI动态物件机制](https://docs.godotengine.org/en/4.6/tutorials/3d/global_illumination/using_lightmap_gi.html#dynamic-objects)
3. VoxelGI也有几何预计算。Godot文档明确指出，Static几何变更需重烘焙，Dynamic模式成本更高；静态烘焙不能使用自定义ShaderMaterial的完整表面结果，会将其作为黑色遮挡物。本项目大量使用`home_surface`等程序材质，因此需要制作可供烘焙的材质代理，不能只给房屋添加VoxelGI节点。[VoxelGI限制](https://docs.godotengine.org/en/4.6/tutorials/3d/global_illumination/using_voxel_gi.html#voxelgi-interaction-with-lights-and-objects)
4. SDFGI可以反映静态区块重建后的布局，但不能把它当作家具连续拖动时完整的实时GI。编辑预览可先用普通光照，确认放置后再分帧刷新相关缓存。[SDFGI动态边界](https://docs.godotengine.org/en/4.6/tutorials/3d/global_illumination/using_sdfgi.html)
5. 反射探针跟随房屋模块，布局、门状态或时间变化后按需重捕获，并分散到不同帧；不要将全部探针设为Always。一次移动造成的捕获峰值和稳态成本须分别测量。[探针更新模式](https://docs.godotengine.org/en/4.6/tutorials/3d/global_illumination/reflection_probes.html)
6. 屋顶剖切、树木淡出属于可读性效果，光照代理不能无意中把真实遮挡也当作消失。室内GI、探针捕获和剖切表现需要一起设计，避免镜头移动导致房间突然漏光。
7. 家具保持独立模块。固定建筑可按模块/区域合批；MultiMesh整组决定可见性，不能跨全岛合并后期待逐件裁剪。Godot的遮挡裁剪本身还占用CPU，宜优先使用简单墙体/建筑代理，在开阔草地未必划算。[MultiMesh](https://docs.godotengine.org/en/4.6/tutorials/performance/using_multimesh.html)、[遮挡裁剪](https://docs.godotengine.org/en/4.6/tutorials/3d/occlusion_culling.html)

**性能成本还包括什么**

| 资源 | 成本来源 | 对本项目的控制方法 |
| --- | --- | --- |
| GPU每帧时间 | 额外屏幕效果、阴影重绘、复杂材质、透明过绘、GI追踪 | 按场景与画质档启用，先逐项测再测组合；用帧时间比较 |
| CPU与提交 | 物件/材质切换、灯与阴影管理、可见性测试、建造后重建 | 共享材质、独立模块内合批、简化遮挡代理、限制单帧更新量 |
| 内存与带宽 | 贴图、阴影图、GI数据、历史帧及降噪缓冲 | 采用合适尺寸和压缩；远景不使用近景资产；避免全场独立材质副本 |
| 包体和加载 | 高分辨率材质、烘焙数据、多档资产及着色器变体 | 主体与近景优先；分区加载；保留导入与预热流程 |
| 制作与维护 | UV2/烘焙代理、材质规范、昼夜调色、移动后的缓存失效 | 先完成一栋房屋与一块户外样板，再扩展到生成器和建造系统 |

例如4K输出约829万像素，是现有200万3D预算的约4.15倍；像素相关工作会显著增长，但固定开销和CPU瓶颈使帧率不会严格按此比例变化。一张4096² RGBA8贴图不含mipmap就占64MiB，完整mipmap约85MiB；压缩格式会改变实际占用，不能用PNG文件大小代表显存。程序纹样也不是免费：复杂数学、采样和高频细节会消耗像素时间。

现有程序生成网格不能只开启导入选项就自动获得合适LOD。Godot的自动LOD主要在导入阶段生成；程序网格需要额外生成LOD数据，例如研究ImporterMesh流程。渲染LOD也不应直接替代独立碰撞。[Godot LOD](https://docs.godotengine.org/en/4.6/tutorials/3d/mesh_lod.html)、[ImporterMesh](https://docs.godotengine.org/en/4.6/classes/class_importermesh.html)

路径追踪还需几何加速结构、求交、着色和降噪，增加GPU及内存成本。id Software负责人披露其路径追踪集成约花费六个月；该开发周期只用于说明技术规模，不能当作本项目工期估计。帧生成改善显示流畅度，也不能替代真实模拟/渲染帧时间的控制。[id Software访谈](https://developer.nvidia.com/blog/how-id-software-used-neural-rendering-and-path-tracing-in-doom-the-dark-ages/)、[Bethesda功能及硬件范围](https://slayersclub.bethesda.net/en-US/news/doom-the-dark-ages-june-2025-pc-update)

**建议的实施顺序与验收**

| 阶段 | 做成什么样 | 成本与验收目标 |
| --- | --- | --- |
| 第一阶段：画面基准和材质样板 | 固定晴天、傍晚、夜景、室内参考；选择色调映射并调曝光/冷暖；改善铜、木、布、石的差异；配置少量反射来源 | 建议均衡档整体新增成本先控制在约1ms以内，属于研发目标而非保证；检查白色角色、三物种、27件服装、UI及所有时段 |
| 第二阶段：一个室内、一个溪谷样板 | 室内比较手工光照、LightmapGI与局部VoxelGI；溪谷比较普通薄雾、局部体积雾和少量动态细节 | 分别记录稳态、首次加载、探针捕获、移动镜头与布局变更的帧时间；确定是否只放高画质档 |
| 第三阶段：释放与分配预算 | 模块内批处理、LOD/裁剪、阴影范围、贴图及特效分级 | 实际走动、跨门、树林遮挡、夜景、雨/雾与多人同屏；检查卡顿、阴影跳变、拖影、漏光和目标可读性 |
| 后续研究 | 全岛SDFGI、复杂天气、密集植被或更高级反射 | 先定义最低硬件和建造系统约束，再决定是否值得投入 |

建议长期保留三个目标档：低档以清晰轮廓、色彩和基本阴影为核心；均衡档沿用约200万像素并使用经过验证的材质/局部光照；高档可按实际收益增加SSIL、局部体积雾或单房间GI。基础美术质量应跨档保持一致。

抗锯齿可先保留4×MSAA。它适合当前卡通轮廓，时序方案则需重点检查树叶、格纹、细线和工具移动时的拖影；如果未来选择FSR2，应重新比较MSAA和时序重建的组合，不能直接叠满所有选项。[Godot抗锯齿](https://docs.godotengine.org/en/4.6/tutorials/3d/3d_antialiasing.html)、[Godot分辨率缩放](https://docs.godotengine.org/en/4.6/tutorials/3d/resolution_scaling.html)

下一轮最值得制作的可评审成果是：**同一菜园镜头的光色与材质样板、同一工坊室内的局部光照对照、同一溪谷的薄雾样板**，每份附画面和帧时间。先选定能让当前画风更有层次的组合，再扩展到整个项目。

本报告没有给出Windows性能结论，也未验证低端显卡、长时间发热、全局GI或新的建造流程。后续画质实现需要另开实际修改与验收，本次发布内容仍为0.3.3的水井、工坊和蝴蝶结修改。
